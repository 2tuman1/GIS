# Задание № 3. Лекция по курсу «Анализ безопасности автоматизированных систем»

Раздел курса: IV. Анализ безопасности сетевой инфраструктуры.

Тема № 7. Анализ сегментации сети и защищенности сетевого взаимодействия компонентов ГИС.

Объект защиты: государственная информационная система предоставления социальных выплат населению.

## Введение

ГИС предоставления социальных выплат принимает заявления граждан, обрабатывает сведения о доходах и составе семьи, проверяет основания для назначения пособий, рассчитывает выплаты и сохраняет результаты рассмотрения. Эти операции выполняются несколькими связанными компонентами: веб-сервером, сервером приложений, сервисом расчёта выплат, системой управления базами данных, рабочими местами сотрудников и служебными серверами.

Сетевая инфраструктура обеспечивает обмен информацией между компонентами. Между веб-сервером и сервером приложений передаются запросы пользователей, между прикладными службами и PostgreSQL — запросы к данным, между сервером резервного копирования и базой — данные для восстановления. Доступ каждого компонента к другим компонентам должен соответствовать его назначению. Сегментация сети и межсетевое экранирование обеспечивают такое разграничение.

Цель лекции — освоить архитектуру сети ГИС, способы разделения её на сегменты, принципы сетевой фильтрации и последовательность проверки разрешённых и запрещённых соединений.

### Учебные задачи

В ходе лекции последовательно рассматриваются три вопроса: какие сетевые взаимодействия необходимы ГИС, как ограничить остальные соединения и каким способом убедиться, что заданные ограничения действительно действуют. Для этого используется одна архитектура с семью сетевыми зонами, перечнем узлов и матрицей из тринадцати разрешённых потоков. На каждом этапе правила связываются с функциями ГИС: приёмом заявления, проверкой сведений, расчётом выплаты, администрированием и регистрацией событий.

Сегментация напрямую связана с тремя свойствами безопасности информации. Конфиденциальность нарушается, когда посторонний узел может обратиться к сервису, который обрабатывает персональные данные. Целостность оказывается под угрозой, если неуполномоченному источнику доступны интерфейсы изменения записей или управления сервером. Доступность страдает, если необходимые рабочие соединения ошибочно блокируются либо один сегмент получает возможность перегружать службы другого. Поэтому качественная политика должна одновременно блокировать ненужное и сохранять необходимые информационные потоки.

К завершению лекции обучающийся должен понимать разницу между физическим и логическим разделением сети, определять путь пакета между двумя узлами, читать правило межсетевого экрана, находить избыточные разрешения и устанавливать связь между сетевой записью и процессом обработки заявления. Отдельное внимание уделяется документированию: невозможно доказать корректность фильтрации, если не зафиксировано, какие соединения считаются допустимыми.

## Учебная архитектура

Во всех примерах используется единая схема ГИС с адресами из частных диапазонов и тестовой внешней сетью `198.51.100.0/24`. Все адреса и сведения используются в учебном примере.

| Зона | Подсеть | Назначение |
|---|---|---|
| EXT | `198.51.100.0/24` | Внешние пользователи тестового веб-портала |
| DMZ | `172.16.10.0/24` | Публичный веб-сервер |
| APP | `10.20.20.0/24` | Сервер приложений и сервис расчёта выплат |
| DB | `10.20.30.0/24` | PostgreSQL с заявлениями и выплатами |
| USR | `10.20.40.0/24` | Рабочие места оператора и инженера |
| ADM | `10.20.50.0/24` | Выделенный узел администрирования |
| SRV | `10.20.60.0/24` | Резервное копирование и сбор журналов |

| Узел | IP-адрес | Назначение |
|---|---|---|
| WEB-GIS | `172.16.10.10` | Веб-сервер для граждан |
| APP-GIS | `10.20.20.11` | Приём и обработка заявлений |
| PAY-GIS | `10.20.20.12` | Расчёт выплат |
| DB-GIS | `10.20.30.10` | PostgreSQL |
| ARM-OP | `10.20.40.21` | АРМ оператора |
| ARM-OP-2 | `10.20.40.22` | Резервное АРМ оператора |
| ARM-ENG | `10.20.40.31` | АРМ инженера |
| JUMP-GIS | `10.20.50.10` | Узел администрирования |
| BACKUP-GIS | `10.20.60.10` | Сервер резервного копирования |
| LOG-GIS | `10.20.60.20` | Сервер регистрации событий |



```text
                         EXT: внешние пользователи
                                  │ HTTPS tcp/443
                                  ▼
                     ┌─────────────────────────┐
                     │        FW-GIS           │
                     │  Логический межсетевой  │
                     │         экран           │
                     └─────────────────────────┘
                          │       │       │
         ┌────────────────┘       │       └────────────────┐
         ▼                        ▼                        ▼
   ┌─────────────┐         ┌─────────────┐         ┌─────────────┐
   │ DMZ         │         │ APP         │         │ DB          │
   │ WEB-GIS     │         │ APP-GIS     │         │ PostgreSQL  │
   │             │         │ PAY-GIS     │         │ DB-GIS      │
   └─────────────┘         └─────────────┘         └─────────────┘
         
   Другие зоны, подключённые через FW-GIS:
   USR: ARM-OP, ARM-ENG
   ADM: JUMP-GIS
   SRV: BACKUP-GIS, LOG-GIS

   Основные разрешённые межсегментные соединения через FW-GIS:

   EXT       → WEB-GIS                 HTTPS tcp/443
   WEB-GIS   → APP-GIS                 HTTPS tcp/8443
   ARM-OP    → APP-GIS                 HTTPS tcp/8443
   APP-GIS   → DB-GIS                  PostgreSQL tcp/5432
   PAY-GIS   → DB-GIS                  PostgreSQL tcp/5432
   ARM-ENG   → JUMP-GIS                HTTPS tcp/443
   JUMP-GIS  → APP-GIS / DB-GIS        SSH tcp/22
   BACKUP-GIS → DB-GIS                 PostgreSQL tcp/5432
   WEB-GIS / APP-GIS / PAY-GIS / DB-GIS → LOG-GIS tcp/6514
```

`FW-GIS` — единый логический межсетевой экран, контролирующий взаимодействие между зонами EXT, DMZ, APP, DB, USR, ADM и SRV. Все рассматриваемые межсегментные соединения проходят через `FW-GIS` и проверяются по правилам фильтрации. Межсетевой экран применяет первое подходящее правило сверху вниз. Ответный трафик разрешённых соединений обрабатывается с учётом состояния сеанса.


### Как читать учебную схему

На схеме сначала определяется источник запроса, затем назначение и сетевой сервис. Стрелка `WEB-GIS → APP-GIS tcp/8443` означает, что именно веб-сервер устанавливает новое TCP-соединение с прикладным сервером. Стрелка не обозначает передачу всех видов трафика в обе стороны. Ответные пакеты относятся к уже установленному соединению и обрабатываются механизмом контроля состояния `FW-GIS`.

Каждый из трёх основных функциональных уровней имеет собственную задачу. Внешний веб-узел принимает запрос и передаёт их прикладной службе. Сервер приложения проверяет права пользователя, выполняет расчётные и регистрационные операции и обращается к базе данных. СУБД выполняет запросы от тех серверов, которым разрешено её использовать. Такое разделение позволяет отдельно контролировать публичный доступ, работу приложений и доступ к хранимой информации.

В таблице сетевых взаимодействий фиксируются не пользователи приложения, а технические соединения между узлами. Пользователь может быть авторизован в личном кабинете, но это не означает, что его компьютер должен иметь сетевой доступ к PostgreSQL. Связь пользователя с базой опосредована сервером приложений, который выполняет разрешённые операции от имени службы.

## 1. Архитектура сетевой инфраструктуры ГИС социальных выплат

Сетевая архитектура описывает состав подключённых узлов, их адресацию, принадлежность к сегментам, пути передачи данных и точки управления трафиком. Для анализа требуется схема сети, реестр активов и перечень разрешённых соединений. Схема показывает топологию, реестр связывает адрес с владельцем и назначением, перечень соединений устанавливает допустимые взаимодействия.

### 1.1. Функции основных компонентов

Веб-сервер принимает HTTPS-запросы граждан и передаёт необходимые запросы серверу приложений. Сервер приложений выполняет бизнес-логику: проверяет заявления, запрашивает сведения и возвращает результат. Сервис расчёта выплат изменяет разрешённые сведения в базе данных. PostgreSQL хранит записи о заявлениях и назначенных выплатах. АРМ оператора обращается к прикладным функциям, а административный узел обеспечивает доступ инженера к серверам. Сервер журналирования собирает события безопасности, а резервный сервер обеспечивает сохранение данных.

### 1.2. Что отображать на схеме

Для каждого узла фиксируют имя, IP-адрес, сегмент, роль, рабочие протоколы, владельца и принадлежность к информационной системе. На схеме показывают сетевые границы, межсетевые экраны и направления инициации соединений. Например, соединение `APP-GIS → DB-GIS tcp/5432` должно быть обозначено как поток от прикладного сегмента к базе данных.

Маршрутизатор доставляет пакеты между сетями; межсетевой экран решает, разрешать ли конкретное соединение. Для анализа важно наличие фильтрации на пути пакетов. Простое разделение адресов по подсетям не гарантирует изоляцию, если маршрутизация между ними не ограничена.

### 1.3. Адресация, подсети и сетевые интерфейсы

IP-адрес позволяет обозначить участника сетевого обмена, а маска сети определяет, какие адреса объединены одним адресным префиксом. Для сегмента APP используется сеть `10.20.20.0/24`, а для базы — `10.20.30.0/24`. В записи `/24` первые 24 бита задают префикс сети. Для сетевых правил такой префикс означает сразу множество потенциальных источников или назначений. Поэтому правило с сетью `/24` существенно шире правила с адресом `/32`, где указан один конкретный узел.

У сервера может быть несколько сетевых интерфейсов. При проектировании необходимо учитывать все пути, по которым он доступен: служебный, административный, резервный и прикладной. Например, наличие на `DB-GIS` дополнительного интерфейса в сети управления не должно превращаться в обход фильтрации между APP и DB. Для проверки используются таблицы адресации, конфигурации интерфейсов, маршруты и перечень подключений.

### 1.4. Коммутация и маршрутизация

Коммутатор передаёт кадры в пределах канального сегмента, ориентируясь на MAC-адреса. Маршрутизатор передаёт IP-пакеты между различными сетями на основе таблицы маршрутизации. Межсетевой экран дополняет передачу пакетов решением о допустимости соединения. В сети ГИС эти функции могут выполняться отдельными устройствами или одним программно-аппаратным комплексом, однако при анализе их назначение разделяют.

Путь `ARM-OP → APP-GIS` пересекает границу сетей `10.20.40.0/24` и `10.20.20.0/24`. Для прохождения запроса необходимо, чтобы маршрутизация обеспечивала доставку пакетов, а правила `FW-GIS` разрешали соединение по `tcp/8443`. Наличие маршрута само по себе не означает разрешения доступа: решение о прохождении трафика принимает точка фильтрации. Отсутствие маршрута, в свою очередь, может блокировать соединение даже при наличии разрешающего правила.

### 1.5. Направления сетевого обмена

В анализе часто выделяют обмен «север — юг» и «восток — запад». Первое обозначает взаимодействие с внешними сетями через границу системы: для ГИС это обращение граждан к `WEB-GIS`. Второе относится к внутренним перемещениям между компонентами: например, `APP-GIS → DB-GIS`, `PAY-GIS → LOG-GIS` или `JUMP-GIS → DB-GIS`. После защиты внешней границы особое значение приобретает именно внутренний обмен, потому что широкое межсегментное правило позволяет одному скомпрометированному компоненту обращаться к соседним системам.

Для ГИС важны и технические потоки, не связанные напрямую с нажатием кнопки в веб-портале: передача журналов, резервное копирование, административные сессии. Они входят в общую архитектуру и должны проходить через те же процедуры инвентаризации и согласования, что и основные операции обработки заявлений.

## 2. Основные принципы сетевой сегментации

Сегментация — разделение сети на части с контролируемыми взаимодействиями. Отдельный сегмент объединяет устройства со сходными функциями и условиями доступа. Границы сегментов позволяют применять правила, ограничивающие распространение несанкционированного доступа.

### 2.1. Основания для разделения

| Основание | Применение в ГИС |
|---|---|
| Функциональное назначение | Публичный веб-сервер, прикладные серверы, СУБД |
| Характер информации | Сегмент DB содержит защищаемые сведения о гражданах |
| Категория пользователей | АРМ операторов отделены от серверных компонентов |
| Административные полномочия | Узел администрирования выделен в ADM |
| Служебные задачи | Резервирование и журналы размещены в SRV |

### 2.2. Что создаёт границу безопасности

Сегмент может быть реализован отдельной подсетью, VLAN, VRF или изолированной виртуальной сетью. Контроль обеспечивается правилами межсетевой фильтрации на маршрутах между сегментами. Дополнительно применяются локальные межсетевые экраны серверов и ограничения на уровне приложений. Схема считается корректной, если каждый предполагаемый канал доступа проходит через установленную точку контроля и не имеет обходного маршрута.

### 2.3. Сокращение последствий компрометации

При компрометации внешнего веб-сервера нарушитель не должен получать произвольный доступ к PostgreSQL, АРМ или узлу администрирования. Разрешённый маршрут ведёт от `WEB-GIS` к `APP-GIS` на конкретный сервисный порт. Прямой поток `WEB-GIS → DB-GIS tcp/5432` в целевой архитектуре отсутствует.

### 2.4. Разница между физическим и логическим разделением

Физическая сегментация означает размещение узлов на отдельных линиях связи, коммутаторах или изолированных инфраструктурах. Логическая сегментация выполняется средствами конфигурации сети: VLAN, отдельными IP-подсетями, виртуальными сетями, VRF и правилами фильтрации. Оба подхода решают задачу разграничения взаимодействий, но логическая сегментация требует особого контроля настроек сетевого оборудования.

VLAN образует отдельный широковещательный домен на канальном уровне. Рабочее место из VLAN пользователей не может напрямую обмениваться Ethernet-кадрами с сервером в VLAN базы данных. Для IP-связи между такими VLAN требуется маршрутизация. Именно на маршрутизируемой границе располагают правила, разрешающие одни потоки и запрещающие другие. Если маршрутизатор разрешает любые межсетевые соединения, само наличие разных VLAN ещё не обеспечивает требуемого ограничения доступа.

Отдельная IP-подсеть также не равнозначна самостоятельной зоне безопасности. Сегмент должен иметь определённую функцию, перечень участников, допустимые связи, владельца правил и точку контроля. Поэтому проектирование начинается с назначения узлов и информационных потоков, а только затем выбираются VLAN и адресные диапазоны.

### 2.5. Последовательность проектирования сегментации

Сначала составляют реестр активов с их назначением и уровнем доступа к данным. Далее компоненты группируют по функциям: внешний веб-сервис, прикладная логика, СУБД, пользователи, администрирование, резервирование и журналы. Для каждой пары групп выясняют, требуется ли обмен, кто его инициирует и каким протоколом пользуется. После этого определяют границы зон, пути маршрутизации и правила фильтрации. Проект завершается проверкой, что необходимая функциональность сохраняется, а неразрешённые подключения блокируются.

В рассматриваемой ГИС граница DB заслуживает отдельного контроля, поскольку именно здесь хранятся записи о гражданах и выплатах. Сервер `APP-GIS` обращается к базе по `tcp/5432`, а `WEB-GIS` прямого доступа к базе не получает. При компрометации веб-сервера наличие такой границы ограничивает доступные нарушителю сетевые направления. Аналогично разделение ADM и USR препятствует произвольным административным подключениям с рабочих мест сотрудников.

### 2.6. Микросегментация и локальная фильтрация

Микросегментация — более детальное разделение взаимодействий, вплоть до отдельных серверов и процессов. Она может строиться на локальных межсетевых экранах, средствах виртуализации и правилах доступа между рабочими нагрузками. Например, внутри одной зоны APP сервер `APP-GIS` и сервис `PAY-GIS` выполняют разные функции. Даже если они используют одну подсеть, их обращения к DB могут быть ограничены разными правилами.

Локальная фильтрация на сервере дополняет межсегментные ограничения. Если на `DB-GIS` разрешены входящие подключения PostgreSQL только от назначенных источников, ошибка в центральном МЭ не сразу приводит к доступности службы со всех внутренних адресов. При этом локальные правила должны быть согласованы с общей матрицей: противоречивые настройки могут нарушить обработку заявлений или резервное копирование.

## 3. Назначение сетевых зон безопасности

Сетевая зона — совокупность компонентов, для которых определены общие правила взаимодействия. В учебной ГИС используются зоны EXT, DMZ, APP, DB, USR, ADM и SRV.

### 3.1. DMZ — демилитаризованная зона

DMZ предназначена для размещения компонентов, принимающих обращения из внешних сетей. Для ГИС таким компонентом является `WEB-GIS`. Он выступает входной точкой для граждан, но не содержит всех функций обработки заявлений и не получает прямого доступа к сетевому сегменту базы данных. Из внешней сети разрешён только `tcp/443` к адресу веб-сервера, а сам веб-сервер может передавать запросы строго определённому прикладному узлу.

Такое построение формирует две самостоятельные границы: EXT → DMZ и DMZ → APP. Даже если веб-сервер обслуживает запросы по HTTPS, это не является основанием для предоставления ему доступа к любым внутренним службам. Вторая граница определяет конкретный канал к приложению. Попытка с `WEB-GIS` обратиться непосредственно к `DB-GIS` по `tcp/5432` должна быть заблокирована.

Сегмент DMZ также удобен для размещения обратного прокси-сервера, который принимает HTTP(S)-запросы и передаёт их разрешённому сервису. На таком узле могут выполняться завершение TLS-соединения, проверка формата запросов, ограничения по частоте обращений и регистрация событий доступа. Обратный прокси и межсетевой экран выполняют разные задачи: первый обрабатывает прикладные запросы, второй ограничивает сетевые связи. Их совместное применение позволяет разделить внешнюю публикацию сервиса и внутреннюю обработку данных.

### 3.2. Зона приложений и зона данных

Зона APP объединяет программы, реализующие процессы предоставления социальных выплат. `APP-GIS` регистрирует и обрабатывает заявления, `PAY-GIS` обслуживает расчётные операции. Зона DB содержит PostgreSQL; её входящие соединения предназначены для известных прикладных и служебных компонентов. При этом правило для APP не должно автоматически разрешать весь диапазон `10.20.20.0/24` к любому серверу DB. Чем конкретнее список клиентов базы, тем проще обнаружить появление неизвестного узла или ошибочного подключения.

Разграничение APP и DB определяет также обязанности компонентов. Сетевой экран решает, может ли прикладной сервер установить TCP-соединение с PostgreSQL. Сама СУБД отдельно выполняет аутентификацию роли и проверяет её разрешения на таблицы. Поэтому политика сегментации защищает путь к сервису данных, а механизмы управления доступом СУБД — операции над данными после подключения.

### 3.3. Зона пользователей и зона администрирования

В зоне USR расположены рабочие станции сотрудников. Оператор использует интерфейс приложения и не должен управлять сервером базы данных. Для инженера предусмотрен административный путь `ARM-ENG → JUMP-GIS → целевой сервер`. Выделенный узел служит точкой управления административными сессиями: здесь могут применяться индивидуальная аутентификация, разграничение административных полномочий и регистрация действий.

Такое построение сокращает число прямых административных соединений. Например, разрешение `JUMP-GIS → DB-GIS tcp/22` позволяет обслуживать сервер СУБД, не открывая SSH для всей сети рабочих мест. Это особенно важно, потому что административный интерфейс предоставляет больше возможностей воздействия на систему, чем пользовательская функция просмотра заявления.

### 3.4. Зона служебных серверов

В зоне SRV находятся `BACKUP-GIS` и `LOG-GIS`. Они выполняют разные операции: резервный сервер обращается к PostgreSQL для создания копий, а сервер журналирования принимает сообщения от веб-, прикладных и серверных компонентов. Из этого следует различная направленность потоков. `BACKUP-GIS` инициирует обращение к `DB-GIS`, в то время как `DB-GIS` направляет события на `LOG-GIS`.

Правило «всем узлам SRV разрешён доступ к DB» делает полномочия сервисов одинаковыми, хотя функции различаются. Оно расширяет поверхность доступа к базе и затрудняет расследование нежелательных подключений. Матрица должна сохранять различие между назначением резервного сервера и сервера журналирования.

## 4. Взаимодействие веб-сервера, сервера приложений, СУБД и АРМ

Взаимодействия формируют цепочку обработки заявления:

1. Гражданин обращается к `WEB-GIS` по HTTPS (`tcp/443`).
2. `WEB-GIS` передаёт прикладной запрос `APP-GIS` по `tcp/8443`.
3. `APP-GIS` выполняет запрос к `DB-GIS` по `tcp/5432`.
4. `PAY-GIS` обращается к `DB-GIS` по `tcp/5432`, если выполняет операцию расчёта выплат.
5. Оператор работает с `APP-GIS` по `tcp/8443`, не обращаясь к СУБД напрямую.
6. Инженер получает доступ к серверу через `JUMP-GIS`, а не через прямое соединение с рабочего места.

### 4.1. Матрица разрешённых информационных потоков

| Код | Источник | Назначение | Протокол/порт | Служебная необходимость |
|---|---|---|---|---|
| A1 | EXT `198.51.100.0/24` | WEB-GIS | tcp/443 | Веб-портал для граждан |
| A2 | WEB-GIS | APP-GIS | tcp/8443 | Передача запросов приложению |
| A3 | ARM-OP | APP-GIS | tcp/8443 | Работа оператора |
| A4 | APP-GIS | DB-GIS | tcp/5432 | Обработка заявлений |
| A5 | PAY-GIS | DB-GIS | tcp/5432 | Учёт выплат |
| A6 | ARM-ENG | JUMP-GIS | tcp/443 | Вход инженера в интерфейс администрирования |
| A7 | JUMP-GIS | APP-GIS | tcp/22 | Администрирование приложения |
| A8 | JUMP-GIS | DB-GIS | tcp/22 | Администрирование СУБД |
| A9 | BACKUP-GIS | DB-GIS | tcp/5432 | Резервное копирование |
| A10 | WEB-GIS | LOG-GIS | tcp/6514 | Передача журналов |
| A11 | APP-GIS | LOG-GIS | tcp/6514 | Передача журналов |
| A12 | PAY-GIS | LOG-GIS | tcp/6514 | Передача журналов |
| A13 | DB-GIS | LOG-GIS | tcp/6514 | Передача журналов |

Матрица описывает инициируемые соединения. Разрешение обратных пакетов для уже установленного соединения обеспечивается механизмом контроля состояния межсетевого экрана. Все потоки, не внесённые в матрицу, должны блокироваться.

### 4.2. Что нужно знать о портах

Порт — числовой идентификатор службы на узле. `tcp/443` применяется для HTTPS, `tcp/5432` — стандартный порт PostgreSQL, `tcp/22` — SSH. В учебной архитектуре сервисный HTTPS-порт приложения выбран как `tcp/8443`, а `tcp/6514` — для передачи журналов по TLS. Указание порта в матрице фиксирует назначение соединения, но не подтверждает безопасность приложения, работающего на этом порту.

### 4.3. Что происходит при обращении гражданина к порталу

Разберём обработку запроса по этапам. Компьютер пользователя с адресом `198.51.100.10` устанавливает HTTPS-соединение с `WEB-GIS` по `tcp/443`. `FW-GIS` сопоставляет параметры пакета с правилами границы EXT–DMZ и пропускает разрешённое соединение. Веб-сервер принимает запрос, после чего самостоятельно инициирует отдельное соединение с `APP-GIS` на `tcp/8443`. Это уже другой сетевой поток, который проверяется на границе DMZ–APP.

Сервер приложения анализирует запрос и выполняет необходимую операцию. Для чтения или изменения данных он открывает отдельное соединение с `DB-GIS` по `tcp/5432`. Пакеты от PostgreSQL возвращаются по установленному соединению к приложению, а прикладной результат передаётся веб-серверу и затем пользователю. Таким образом, одна пользовательская операция проходит через несколько отдельных соединений, каждое из которых имеет собственные источник, назначение и допустимые параметры.

```text
1) CITIZEN → WEB-GIS   : tcp/443    разрешено
2) WEB-GIS → APP-GIS   : tcp/8443   разрешено
3) APP-GIS → DB-GIS    : tcp/5432   разрешено
4) WEB-GIS → DB-GIS    : tcp/5432   запрещено
5) CITIZEN → DB-GIS    : tcp/5432   запрещено
```

Обработка заявления не требует, чтобы пользователь видел внутренний IP-адрес PostgreSQL или мог открывать TCP-соединения с сервером базы. Сетевые полномочия прикладных узлов не наследуются автоматически внешним пользователем.

### 4.4. Порты источника и назначения

При установлении TCP-соединения клиент выбирает исходный порт, а удалённый сервис прослушивает свой порт назначения. Например, соединение с `APP-GIS` может иметь исходный порт `52134` и порт назначения `8443`. Для межсетевой политики существенна разрешённая инициатива от конкретного клиента к служебному порту. Контроль состояния позволяет принять ответные пакеты в рамках той же TCP-сессии без отдельного правила, разрешающего запуск новых соединений в обратном направлении.

В описании правила важно указывать протокол: `tcp/443` и `udp/443` представляют собой разные виды соединений. Значение `any` расширяет разрешение не только на один ожидаемый порт, а на весь набор портов и, в зависимости от формата политики, протоколов. Такое разрешение требует отдельного обоснования.

### 4.5. Сетевой доступ и доступ к информации

Прохождение TCP-соединения подтверждает лишь то, что пакеты достигли соответствующей службы. Пользовательская аутентификация, проверка роли и разрешение на обработку записи выполняются на прикладном уровне. Поэтому при разборе события различают три вопроса: разрешён ли сетевой поток, ответила ли служба и удалось ли выполнить прикладную операцию.

Например, запись `APP-GIS → DB-GIS tcp/5432 allow` не доказывает чтения персональных данных. Для установления результата соединения потребуются сведения PostgreSQL об аутентификации и выполненных действиях. Напротив, запись `WEB-GIS → DB-GIS tcp/5432 deny` уже подтверждает, что сетевой экран заблокировал неразрешённое направление обращения к базе.

## 5. Угрозы несанкционированного сетевого доступа

Несанкционированный сетевой доступ возникает, когда субъект соединяется с узлом или службой вне установленных полномочий. Причиной становятся широкие правила фильтрации, ошибки сегментации, незарегистрированные устройства и обход административных каналов.

| Угроза | Пример в учебной ГИС | Возможные последствия |
|---|---|---|
| Прямой доступ к СУБД | WEB-GIS соединяется с DB-GIS по 5432 | Доступ к сервису данных в обход прикладного уровня |
| Избыточные разрешения | Вся USR может обращаться к любому серверу APP на любом порту | Возможность доступа к ненужным службам |
| Неучтённое устройство | `10.20.20.99` подключается к DB-GIS | Доступ неизвестного узла к серверу с ПДн |
| Обход узла администрирования | ARM-ENG подключается по SSH непосредственно к PAY-GIS | Нарушение установленного порядка администрирования |
| Публикация внутреннего приложения | EXT подключается прямо к APP-GIS | Обход DMZ и публичного веб-узла |
| Избыточный служебный доступ | LOG-GIS соединяется с DB-GIS по 5432 | Лишний доступ служебного сервера к базе |
| Отсутствие необходимых разрешений | PAY-GIS не может отправить журнал на LOG-GIS | Потеря записей значимых событий |

Наличие записи о соединении подтверждает сетевую попытку и принятое межсетевым экраном решение. Оно не доказывает успешную аутентификацию в приложении или изменение данных: эти события проверяются по журналам соответствующих компонентов.

### 5.1. Как появляется путь несанкционированного доступа

Для анализа угроз полезно рассматривать последовательность «исходный узел → доступный сетевой сервис → возможное воздействие». Например, если правило разрешает всей зоне USR подключения к любому серверу APP, то любая рабочая станция получает сетевой доступ к дополнительным сервисам приложений. В числе этих сервисов могут оказаться административные интерфейсы, диагностические порты или вспомогательные API. Чем шире правило, тем больше возможностей для нежелательных обращений при компрометации одного рабочего места.

Наличие сетевого доступа само по себе не означает успешного нарушения безопасности, но оно создаёт условия для последующих действий. Поэтому на первом этапе анализа важно выявить неожиданные связи, а на следующих — оценить уязвимости принимающей службы, её средства аутентификации и данные, с которыми она работает.

### 5.2. Основные источники сетевых рисков

Одна группа рисков связана с публикацией внутренних сервисов. Если внешнему пользователю разрешён доступ непосредственно к `APP-GIS`, он минует предусмотренную входную точку DMZ. Вторая связана с чрезмерными правами внутри системы: правило для всей подсети APP открывает доступ к DB новому узлу, который не входит в перечень клиентов PostgreSQL. Третья — с ошибками административного доступа, при которых рабочие места получают прямую возможность подключаться к SSH-сервисам серверов.

Отдельный риск создаёт отсутствие наблюдаемости. Если запрещающие правила не журналируются, отдельные попытки обращения к защищённым сервисам остаются без отражения в контрольных записях МЭ. Это затрудняет установление источника подключения, периода активности и последовательности событий. В обратную сторону, чрезмерное журналирование без правил хранения и отбора создаёт большой объём записей и усложняет поиск значимых событий.

### 5.3. Пример оценки одного сценария

Рассмотрим ситуацию: сервер с адресом `10.20.20.99` начинает обращаться к `DB-GIS` по `tcp/5432`. Адрес входит в подсеть APP, но отсутствует в реестре компонентов. Если правило разрешает весь диапазон `10.20.20.0/24`, межсетевой экран примет соединение как допустимое. Причина отклонения от политики — слишком широкий перечень разрешённых источников. Исправление состоит в замене разрешения для подсети точными адресами `APP-GIS` и `PAY-GIS` и в проверке происхождения нового узла.

Этот сценарий демонстрирует связь инвентаризации и фильтрации: одна только корректная запись IP-префикса не позволяет отличить штатный сервер от неучтённого устройства. Контроль доступа должен опираться на достоверный реестр активов и заранее согласованные информационные потоки.

### 5.4. Влияние ошибочной блокировки на доступность

Ошибка в правилах может не только открыть лишний доступ, но и нарушить работу ГИС. Если заблокирован поток `PAY-GIS → DB-GIS tcp/5432`, система не сможет выполнить предусмотренные операции учёта выплат. Если запрещена передача журналов на `LOG-GIS`, события безопасности перестанут поступать в централизованное хранилище. Такие ситуации относят к ошибочной блокировке необходимого трафика.

При оценке находок поэтому используют две группы отклонений: **лишние разрешения** и **отсутствующие необходимые разрешения**. Первая группа увеличивает риск несанкционированного доступа, вторая приводит к нарушению функций и средств контроля. Правильная политика должна исключать обе группы.

## 6. Механизмы межсетевой фильтрации

Межсетевой экран сопоставляет параметры трафика с правилами безопасности. Правило включает источник, назначение, протокол, порт, действие и параметры регистрации событий. Для учебного `FW-GIS` правила обрабатываются последовательно: используется первое подходящее правило.

### 6.1. Пример правила

```text
Источник:  10.20.20.11/32 (APP-GIS)
Назначение: 10.20.30.10/32 (DB-GIS)
Протокол:  TCP
Порт:      5432
Действие:  allow
```

Это правило предоставляет доступ только серверу приложений к PostgreSQL. Запись `10.20.20.0/24 → 10.20.30.0/24 tcp/5432` охватывает гораздо больше узлов. Маска `/32` означает один конкретный IPv4-адрес, `/24` — сеть из 256 адресов (включая адрес сети и широковещательный адрес).

### 6.2. Порядок правил и перекрытие

Если сначала стоит широкое разрешение `USR/24 → APP/24 any allow`, то следующее более точное правило `ARM-OP → APP-GIS tcp/8443 allow` не будет применено для совпадающих подключений. Такое правило называют перекрытым или недостижимым для соответствующего потока. Поэтому при аудите проверяют порядок правил, а не только содержание каждой строки.

### 6.3. Уровни контроля

Сетевые, локальные и прикладные средства фильтрации контролируют разные участки обмена. Для аудита важно установить, где выполняется каждый вид проверки и какие события фиксируются на соответствующем уровне.

### 6.4. Из каких полей состоит политика МЭ

Правило межсетевого экрана обычно описывает источник, назначение, протокол, порт, действие и параметры журналирования. В некоторых продуктах дополнительно используются имена зон, сетевые объекты, пользовательские группы, время действия и сведения о владельце. Для проверки логики важно привести эти поля к единому смыслу, потому что один и тот же IP-адрес может быть представлен как отдельный узел, диапазон или объект адресной группы.

| Поле | Пример | Как интерпретировать |
|---|---|---|
| Источник | `10.20.20.11/32` | Соединение может инициировать только APP-GIS |
| Назначение | `10.20.30.10/32` | Целью является DB-GIS |
| Протокол и порт | `tcp/5432` | Разрешается конкретный TCP-сервис PostgreSQL |
| Действие | `allow` | Совпавшее новое соединение разрешается |
| Регистрация | `log=on` | Событие решения записывается в журнал по заданной политике |
| Комментарий | «Обработка заявлений» | Указано функциональное основание разрешения |

### 6.5. Последовательность обработки пакета

Для учебного `FW-GIS` применяется обработка по первому совпадению. Межсетевой экран извлекает параметры соединения, затем последовательно сравнивает их с условиями R1, R2, R3 и следующих правил. Как только найдено первое подходящее правило, к соединению применяется его действие; последующие строки для данного решения не рассматриваются. Поэтому расположение правил составляет часть политики безопасности.

Рассмотрим пару:

```text
1. 10.20.40.0/24  → 10.20.20.0/24  any       allow
2. 10.20.40.21/32 → 10.20.20.11/32 tcp/8443  allow
3. any            → any            any       deny
```

Соединение оператора `10.20.40.21 → 10.20.20.11 tcp/8443` попадает под первую строку и разрешается. Вторая строка содержит более точное правило, но уже не участвует в принятии решения. При этом и прямой SSH-запрос инженера к серверу расчёта выплат тоже может попасть под широкое первое разрешение. Для устранения ошибки первое правило убирают, а точные разрешения оставляют отдельно.

### 6.6. Запрет по умолчанию

Принцип запрета по умолчанию означает, что отсутствие явного разрешения приводит к блокировке нового соединения. Его удобно реализовать завершающим правилом `any → any deny` после списка разрешённых потоков. Это позволяет заранее определить, какие взаимодействия необходимы ГИС. Когда новая служба пытается установить связь, её поток не проходит автоматически: для разрешения нужно установить назначение, владельца и допустимые параметры соединения.

Запрещающее правило дополняют регистрацией значимых попыток. Например, записи о блокировке `WEB-GIS → DB-GIS tcp/5432` показывают обращение в обход архитектуры, а записи об отказе `ARM-ENG → PAY-GIS tcp/22` — попытку прямого администрирования. По журналу можно установить, какой источник обращался к защищаемому узлу и какое правило приняло решение.

### 6.7. Контроль состояния соединения

TCP-соединение включает установление связи, передачу данных и завершение. Stateful-МЭ отслеживает набор параметров соединения и допустимые изменения его состояния. Когда инициирующий пакет от `APP-GIS` к `DB-GIS` разрешён, обратный трафик базы относится к этому же соединению. Новый запрос, который база попыталась бы инициировать к приложению, проверяется независимо от существующего разрешения.

Это позволяет формулировать матрицу как перечень инициируемых соединений. Не требуется автоматически добавлять симметричные правила `DB-GIS → APP-GIS tcp/5432`, поскольку ответные пакеты уже разрешённой TCP-сессии обрабатываются механизмом контроля состояния. Для анализа важно различать ответ на запрос и новое соединение, инициированное другой стороной.

### 6.8. Фильтрация адресов и контроль приложений

Сетевые правила вида «адрес — адрес — порт» позволяют ограничить доступ к конкретным сервисам. Однако одинаковый номер порта сам по себе не подтверждает, что по нему работает ожидаемое приложение. Для дополнительной защиты могут применяться средства анализа прикладных протоколов, ограничения запросов и механизмы веб-защиты. Их назначение отличается от сегментации: сетевой МЭ определяет допустимые направления обмена, а прикладные средства проверяют содержимое и контекст запросов.

В примере с ГИС разрешение `EXT → WEB-GIS tcp/443` определяет входной сетевой канал портала. Проверка формата HTTP-запросов, пользовательских сессий и доступа к чужому заявлению выполняется другими механизмами. Рассмотрение этих механизмов вместе позволяет связать сетевую и прикладную безопасность, не смешивая результаты их проверок.

## 7. Принцип минимально необходимого сетевого взаимодействия

Для каждой служебной функции задают только необходимые соединения. Источником, назначением и портом должны быть конкретные компоненты, если их перечень известен. Новые соединения добавляют после определения владельца и назначения. Неиспользуемые разрешения анализируют, а временные правила удаляют по завершении работ.

### Принципы фильтрации П1–П6

| Код | Принцип | Проверяемый признак |
|---|---|---|
| П1 | Запрет по умолчанию | После разрешающих правил есть `deny` для остальных соединений |
| П2 | Минимально необходимый доступ | Источник, назначение и порт точно соответствуют согласованной матрице |
| П3 | Контроль межсегментных границ | Нет прямого EXT → APP/DB и DMZ → DB; используются согласованные маршруты |
| П4 | Выделенное администрирование | Подключения к управляемым серверам идут через JUMP-GIS |
| П5 | Регистрация и контроль событий | Запрещённые попытки журналируются, журналы доступны для проверки |
| П6 | Управление правилами | Нет необоснованных временных, перекрытых и избыточных правил; изменения документируются |

П1–П6 — учебная контрольная таблица, составленная на основе требований к сегментации и межсетевому экранированию. Для оценки каждого правила используется одновременно матрица разрешённых потоков и схема сегментов.

### 7.1. Разрешения для резервных компонентов

Резервный узел может не создавать соединений в выбранный день. Отсутствие записи в журнале не служит основанием для немедленного удаления необходимого разрешения. Перед изменением правила проверяют его назначение, сведения об эксплуатации резервного компонента и порядок переключения.

### 7.2. Подготовка матрицы по принципу минимального доступа

Для каждого разрешения сначала фиксируют выполняемую функцию. Например, «приём заявления через внешний портал» соответствует соединению EXT → WEB-GIS по `tcp/443`, а «чтение и изменение данных заявления прикладной службой» — соединению APP-GIS → DB-GIS по `tcp/5432`. Эти основания превращают матрицу в документ, по которому можно проверить любую строку политики МЭ. Если правило не связано с определённой функцией, его назначение требует уточнения.

Следующий шаг — ограничение источника и назначения. Для PostgreSQL в матрице перечислены конкретные клиенты: `APP-GIS`, `PAY-GIS` и `BACKUP-GIS`. Правило для всей подсети APP или SRV не равноценно этим трём разрешениям: оно охватывает дополнительные узлы, которым доступ к базе не предусмотрен. Затем ограничивается сервисный порт и устанавливается действие. В завершение определяется порядок регистрации событий и ответственный за сохранение правила в политике.

### 7.3. Управление изменениями политики

При изменении архитектуры может появиться новый прикладной сервис, которому необходимо обращаться к существующему узлу. Добавление разрешения начинается с заявки, содержащей источник, назначение, назначение взаимодействия, протокол, порт и срок действия. После согласования администратор вносит правило, а ответственный за безопасность проверяет, что оно не открывает дополнительные направления доступа. Затем выполняется контрольное соединение и фиксируется результат.

Изменения правил должны быть воспроизводимыми. Для этого сохраняют предыдущую конфигурацию, номер изменения, перечень добавленных и удалённых строк и результаты проверки. Если после изменения перестаёт работать критическая функция, предусматривается возврат к согласованной политике. Записи о предыдущем состоянии облегчают сравнение конфигураций и выявление несанкционированных изменений.

### 7.4. Временные и неиспользуемые правила

Временное правило создаётся для ограниченной задачи: диагностики, переноса сервиса или обновления. У него должен быть известный владелец, назначение и срок прекращения действия. Постоянное разрешение «на время наладки» фактически превращается в необоснованный канал доступа. Поэтому при периодическом анализе изучают комментарии, заявки и сведения об использовании правил.

При этом отсутствие соединений за один интервал наблюдения не означает, что правило лишнее. Службы резервного копирования и восстановления, аварийного управления или периодической синхронизации могут работать редко. Решение об удалении принимают после проверки функциональной потребности, а не только по счётчику срабатываний.

## 8. Типы и классы защиты межсетевых экранов по требованиям ФСТЭК

Требования к межсетевым экранам утверждены приказом ФСТЭК России от 09.02.2016 № 9. Они разделяют МЭ по месту применения на пять типов.

| Тип | Назначение |
|---|---|
| А | Межсетевой экран уровня сети |
| Б | Межсетевой экран уровня логических границ сети |
| В | Межсетевой экран уровня узла |
| Г | Межсетевой экран уровня веб-сервера |
| Д | Межсетевой экран уровня промышленной сети |

Предусмотрены классы защиты: для типов А, Б, В — с 1-го по 6-й, для Г и Д — с 4-го по 6-й. Класс защиты — характеристика соответствия МЭ установленным требованиям, а не номер сетевой зоны. Для разделения логических зон рассматриваемой ГИС функционально подходит МЭ типа Б; выбор конкретного продукта и требуемого класса выполняется по установленным требованиям к системе и условиям применения.

При проверке МЭ как средства защиты рассматривают его назначение, подтверждение соответствия, область применения и реализованные функции безопасности. При аудите политики работающего МЭ дополнительно проверяют настройку конкретных правил, их порядок и фактические результаты фильтрации.

### 8.1. Для чего используются типы МЭ

Тип межсетевого экрана характеризует уровень и условия его применения. МЭ уровня сети применяется для контроля трафика между сетевыми сегментами, уровня логических границ сети — для разделения логических областей взаимодействия, уровня узла — для контроля соединений конкретного устройства. Средства уровня веб-сервера ориентированы на защиту веб-взаимодействий, а межсетевые экраны уровня промышленной сети — на соответствующую технологическую инфраструктуру.

В схеме ГИС `FW-GIS` контролирует переходы между зонами EXT, DMZ, APP, DB, USR, ADM и SRV. При обосновании его применения нужно показать, какие границы он защищает, какие функции фильтрации реализует и каким требованиям должен соответствовать. Тип и класс защиты не заменяют анализ правил: даже средство с подтверждёнными характеристиками допускает ошибки при настройке слишком широких разрешений.

### 8.2. Смысл класса защиты и подтверждения соответствия

Класс защиты относится к установленному набору требований безопасности самого межсетевого экрана. Он характеризует не «важность» подсети и не количество заблокированных пакетов, а соответствие определённым требованиям к средству. При выборе устройства рассматривают установленный для системы набор требований, функции МЭ, область применения и документы о подтверждении соответствия.

При проверке внедрённого средства отдельно оценивают его идентификационные данные: модель, версию, состав программных компонентов, настройки и условия эксплуатации. Затем сопоставляют установленную конфигурацию с матрицей взаимодействий. Так различаются две задачи: оценка характеристик МЭ как продукта и проверка того, насколько правильно это средство настроено для защиты ГИС.

### 8.3. Дополнительные механизмы защиты границ

На сетевых границах могут применяться фильтрация по состоянию соединения, разделение интерфейсов по зонам, ограничение доступных сервисов, средства обнаружения вторжений и централизованный сбор журналов. Развёртывание каждого механизма связано с конкретным требованием безопасности. Например, сегментация отделяет базу данных от публичного веб-сервиса, журналирование обеспечивает возможность установить время и источник подозрительного обращения, а контроль конфигураций позволяет выявить появление нового широкого правила.

Для последующего анализа полезно заранее определить, какие сведения должен предоставлять МЭ: перечень правил, порядок их обработки, активные соединения, события разрешений и запретов, изменения конфигурации и источники времени. Такой набор данных позволяет проверить не только схему сети, но и её фактическое функционирование.

## 9. Методы анализа сетевой доступности

Анализ сетевой доступности определяет, какие узлы и службы доступны друг другу при действующей политике. Источниками служат схема сети, таблица маршрутов, конфигурации МЭ, инвентаризация и журналы соединений.

### 9.1. Документарная проверка

Сопоставляют адреса узлов с подсетями, проверяют перечень разрешённых потоков, назначение портов, корректность сетевых маршрутов и границы фильтрации. Находят соединения, отсутствующие в матрице, правила с чрезмерно широкими источниками, назначениями или протоколами.

### 9.2. Анализ журнала соединений

В журнале учитывают источник, назначение, протокол, порт, время, действие МЭ и идентификатор сработавшего правила. По IP-адресу определяют зону узла и его наличие в реестре. Затем сравнивают с матрицей. Например, запись `WEB-GIS → DB-GIS tcp/5432 allow` означает наличие разрешения, которого нет в целевой политике.

### 9.3. Проверочные подключения

На изолированном стенде выполняют контрольные попытки соединений. Разрешённый поток должен проходить через МЭ, запрещённый — блокироваться и фиксироваться в журнале. Результаты сетевой проверки оценивают вместе с доступностью службы: открытое сетевое соединение ещё не подтверждает успешного входа в приложение.

Примеры команд для учебной среды:

```bash
# Проверка установления TCP-соединения до сервиса БД с разрешённого узла
nc -vz 10.20.30.10 5432

# Проверка сервиса приложения
nc -vz 10.20.20.11 8443

# Просмотр установленных и прослушиваемых TCP-портов на сервере Linux
ss -ltn
```

Проверочные подключения выполняют в пределах согласованных адресов и утверждённой программы проверки. Результаты сопоставляют с журналами МЭ и доступностью целевых служб.

### 9.4. Что именно означает доступность сервиса

Проверка доступности состоит из нескольких отдельных уровней. Сначала устанавливают, существует ли маршрут от источника к назначению. Затем анализируют, пропускает ли межсетевой экран нужный протокол и порт. После этого определяют, принимает ли целевой сервер соединение, и, наконец, отвечает ли прикладной сервис корректным образом. Например, успешное установление TCP-соединения по `tcp/5432` ещё не подтверждает успешную аутентификацию в PostgreSQL или право читать таблицы.

При проверке доступа оператор должен различать отказ МЭ, отсутствие службы, сетевую потерю и отказ прикладной аутентификации. Ошибочное смешение этих состояний приводит к неправильным рекомендациям: открытие нового сетевого порта не исправит отсутствие прав пользователя в приложении, а изменение пароля не поможет, если соединение блокируется на границе сегментов.

### 9.5. Анализ маршрутов и интерфейсов

Для проверки сетевого пути используются конфигурации шлюзов и маршрутизаторов, таблицы маршрутов серверов и сведения о сетевых интерфейсах. Пример команды Linux для просмотра маршрутизации:

```bash
ip route
ip -br address
```

Первая команда показывает известные системе маршруты и шлюзы, вторая — адреса и состояние интерфейсов. Сопоставление этих данных со схемой позволяет установить, через какой интерфейс сервер направляет соединение к другому сегменту. Если у компонента есть неожиданная дополнительная сетевая связь, её также нужно отразить на схеме и проверить на прохождение через установленную точку фильтрации.

### 9.6. Чтение и интерпретация журналов

Для анализа межсетевого экранирования полезны следующие поля записи:

| Поле | Пример значения | Смысл |
|---|---|---|
| Время | `2026-11-26 10:15:32` | Когда зафиксирована попытка |
| Источник | `10.20.40.31` | Откуда инициировано соединение |
| Назначение | `10.20.20.12` | К какому узлу направлено соединение |
| Протокол | `tcp` | Тип транспорта |
| Порт назначения | `22` | К какому сервису обращался источник |
| Действие | `deny` | Решение фильтрации |
| Правило | `R16` | Какая строка политики сработала |

Затем адреса переводят в имена узлов по реестру: `10.20.40.31` — `ARM-ENG`, `10.20.20.12` — `PAY-GIS`. Соединение `ARM-ENG → PAY-GIS tcp/22` отсутствует в матрице и не соответствует схеме администрирования. Следовательно, `deny` является правильным результатом. При исследовании важно оценивать не само количество запретов, а соответствие решения ожидаемой политике.

Если журнал содержит только `allow` и не фиксирует запрещённые попытки, невозможно полноценно восстановить картину отклонённых соединений. Для анализа отдельно оценивают включение регистрации на запретах, сохранность журналов, единое время компонентов и возможность сопоставлять события по адресам и идентификаторам правил.

### 9.7. Сравнение ожиданий с фактической политикой

Для каждого проверяемого потока формируют ожидаемое действие `allow` или `deny`. Далее находят первое подходящее правило в текущей конфигурации и записывают фактическое действие. Если ожидаемое и фактическое решения не совпадают, фиксируется отклонение. Такой способ позволяет проверять как штатные соединения, так и нежелательные попытки доступа.

| Поток | Ожидается | Причина |
|---|---|---|
| ARM-OP → APP-GIS `tcp/8443` | `allow` | Рабочая функция оператора |
| ARM-OP → DB-GIS `tcp/5432` | `deny` | Нет прямого доступа оператора к PostgreSQL |
| WEB-GIS → DB-GIS `tcp/5432` | `deny` | Обращение к базе выполняет только приложение |
| BACKUP-GIS → DB-GIS `tcp/5432` | `allow` | Создание резервных копий |
| ARM-ENG → PAY-GIS `tcp/22` | `deny` | Администрирование выполняется через JUMP-GIS |

Для необходимого потока дополнительно проверяют работоспособность сервиса после применения правила. Для запрещённого — отсутствие возможности инициировать соединение и появление соответствующей записи в журнале. Результаты фиксируют так, чтобы их можно было повторить после изменения конфигурации.

## 10. Проверка правил межсетевого экранирования

Проверка должна учитывать топологию, назначение компонентов, последовательность правил и их фактическое использование.

### 10.1. Проверка одной записи журнала

Дана запись:

```text
src=10.20.40.31  dst=10.20.20.12  proto=tcp  dport=22
```

Адрес `10.20.40.31` принадлежит ARM-ENG из зоны USR, `10.20.20.12` — PAY-GIS из APP. Матрица не разрешает прямое SSH-соединение инженера к PAY-GIS. Согласованный административный путь проходит через JUMP-GIS. Следовательно, попытка должна быть запрещена. Если она разрешена правилом для всей подсети USR, правило нарушает П2 и П4.

### 10.2. Проверка перекрытого правила

```text
R3:  10.20.40.0/24 → 10.20.20.0/24  any      allow
R4:  10.20.40.21/32 → 10.20.20.11/32 tcp/8443 allow
```

Когда пакет от ARM-OP к APP-GIS совпадает с R3, до R4 обработка не доходит. Поэтому запись R4 не ограничивает широкое правило R3. Исправление — удалить R3 и сохранить точное разрешение ARM-OP → APP-GIS.

### 10.3. Этапы анализа Э1–Э6

| Этап | Действия | Результат |
|---|---|---|
| Э1. Сбор данных | Получить зоны, реестр узлов, матрицу разрешённых потоков, правила МЭ и журнал | Комплект исходных данных |
| Э2. Инвентаризация | Сопоставить наблюдаемые внутренние адреса с реестром | Неучтённые и не наблюдавшиеся узлы |
| Э3. Анализ потоков | Определить для каждой записи зоны, первое подходящее правило и соответствие матрице | Таблица разрешённых, запрещённых и ошибочно обработанных соединений |
| Э4. Аудит правил | Проверить порядок и содержание всех правил по П1–П6 | Перечень избыточных, перекрытых и недостающих правил |
| Э5. Оценка находок | Описать нарушение, возможные последствия и приоритет исправления | Реестр находок |
| Э6. Исправление и контроль | Подготовить новую политику, план изменения, разрешённые и запрещённые тесты | Исправленный набор правил и программа повторной проверки |

### 10.4. Оценка значимости находок

Для учебного аудита используется простая шкала: высокий приоритет — открытый несанкционированный доступ к DB или внутренним приложениям; средний — избыточное разрешение, создающее дополнительный путь доступа, или отсутствие необходимого защитного контроля; низкий — неиспользуемые и перекрытые правила, недостатки документирования. Окончательная оценка опирается на последствия для обработки заявлений, расчёта выплат и безопасности персональных данных.

### 10.5. Как находить ошибочные и перекрытые правила

Аудит начинается с сопоставления каждой строки с согласованной матрицей потоков. После этого проверяется объём адресов, портов и протоколов. Широкое разрешение может быть ошибочным даже при наличии среди его адресов штатных узлов. Например, `10.20.20.0/24 → 10.20.30.0/24 tcp/5432 allow` включает два необходимых клиента PostgreSQL, но разрешает также другие адреса прикладной сети, для которых доступ к базе не предусмотрен.

Перекрытие рассматривают с учётом порядка правил. Если более ранняя строка разрешает `USR/24 → APP/24 any`, то более позднее точное разрешение `ARM-OP → APP-GIS tcp/8443` не определяет фактическое решение для этого потока. В реестре находок отражают обе проблемы: избыточное разрешение ранней строки и отсутствие самостоятельного эффекта у более позднего правила. Исправление состоит не в перестановке точного правила вниз, а в устранении необоснованного широкого доступа.

Отдельно выявляют неиспользуемые правила, несогласованные временные исключения и запреты без регистрации. У каждого отклонения записывают причину, возможные последствия и корректирующее действие. Приоритет зависит от защищаемого сегмента: открытый доступ к DB из внешнего или пользовательского сегмента требует более срочного внимания, чем дублирующая строка, которая не меняет фактическое действие МЭ.

### 10.6. Полный разобранный пример

Предположим, в настройке МЭ имеются следующие правила:

```text
R1  EXT/24          → WEB-GIS          tcp/443   allow
R2  WEB-GIS         → APP-GIS          tcp/8443  allow
R3  10.20.40.0/24   → 10.20.20.0/24    any       allow
R4  ARM-OP          → APP-GIS          tcp/8443  allow
R5  10.20.20.0/24   → 10.20.30.0/24    tcp/5432  allow
R6  any             → any              any       deny
```

Строки R1 и R2 соответствуют предусмотренным соединениям. Строка R3 разрешает весь трафик от пользовательского сегмента к прикладному, вследствие чего из него доступны не только пользовательский интерфейс, но и прочие сетевые службы. Строка R4 формально точно описывает штатную работу оператора, однако для его подключения уже срабатывает R3. Строка R5 делает PostgreSQL доступным для всех адресов APP, тогда как согласованная матрица содержит ограниченный перечень клиентов. Строка R6 формирует запрет по умолчанию, но должна дополняться регистрацией значимых запрещённых обращений.

Результат анализа оформляется следующим образом:

| Объект проверки | Отклонение | Исправление | Проверка результата |
|---|---|---|---|
| R3 | Избыточный доступ USR к APP | Удалить широкое разрешение | `ARM-ENG → PAY-GIS tcp/22` блокируется |
| R4 | Перекрыто предыдущим правилом | Сохранить точный доступ после удаления R3 | `ARM-OP → APP-GIS tcp/8443` разрешается |
| R5 | Все узлы APP могут обращаться к DB | Разрешить только APP-GIS и PAY-GIS | Другие адреса APP к `tcp/5432` блокируются |
| R6 | Отсутствие журнала запрещённых попыток | Настроить регистрацию отказов | Запреты видны в журнале МЭ |

Этот пример демонстрирует, почему проверка только существования разрешения недостаточна. Нужно определить его область действия и первое подходящее правило для каждого сетевого потока.

### 10.7. Программа повторной проверки

После исправления политики выполняют набор положительных и отрицательных тестов. Положительные должны подтвердить доступность операций ГИС: вход гражданина на портал, передачу запроса к приложению, обращение приложения к PostgreSQL, работу оператора и резервное копирование. Отрицательные должны подтвердить блокировку: прямого доступа из EXT к APP и DB, обращения веб-сервера к DB, SSH с пользовательских рабочих мест в обход JUMP-GIS и доступа неучтённого адреса к PostgreSQL.

Результаты фиксируются по схеме «исходный узел — целевой узел — сервис — ожидаемое действие — фактическое действие — доказательство». В качестве доказательств используются идентификатор правила, журнал события, результаты контрольного соединения и версия конфигурации. Если появляется отклонение, администратор проверяет порядок правил, адресные группы, актуальность маршрутов и локальную фильтрацию на узлах.

### 10.8. Оформление результатов аудита

Отчёт должен позволять восстановить ход проверки. В нём указывают сетевые зоны и узлы, исходную матрицу потоков, версию проверенной политики, обнаруженные несоответствия и предложения по их устранению. Для каждой находки важно отделить факт от его возможного последствия. Например: факт — правило разрешает всей подсети USR доступ на все порты APP; последствие — пользователи получают сетевой путь к ненужным служебным интерфейсам; исправление — заменить правило точным разрешением к `APP-GIS tcp/8443`.

Список найденных нарушений завершается планом изменения конфигурации и повторной проверкой. Такой формат связывает выводы аудита с конкретными действиями и позволяет подтвердить, что после исправления защита усилена, а основные функции системы продолжают работать.

### 11.1. Приказ ФСТЭК России № 117 и требования к ГИС

Приказ ФСТЭК России от 11.04.2025 № 117 устанавливает требования к защите информации в государственных информационных системах и иных указанных в нём системах. Для рассматриваемой темы существенно положение пункта 63 о сегментации и межсетевом экранировании. С ним связаны мероприятия по контролю конфигураций, мониторингу безопасности, ограничению удалённого и привилегированного доступа, а также контролю защищенности.

Применение требований начинается с определения границ и состава ГИС. Затем устанавливают необходимые связи между компонентами, выбирают технические меры и документируют их выполнение. При сетевом аудите это выражается в проверке того, что границы между зонами действительно контролируются, а разрешённые соединения соответствуют функциям системы.

### 11.2. Мера МСЭ.1 — сегментация сети

Мера МСЭ.1 методического документа ФСТЭК от 12.04.2026 посвящена разделению информационной системы на сегменты и контролю сетевых взаимодействий между ними. Для учебной архитектуры она отражена в выделении отдельных зон DMZ, APP, DB, USR, ADM и SRV. Результатом применения меры служит не только рисунок сети, но и перечень границ с контролируемыми соединениями.

Проверка включает наличие обоснованного разделения компонентов, соответствие узлов их зонам, отсутствие обходных каналов и наличие документов, описывающих порядок взаимодействия. Именно поэтому в методике Э1–Э2 сначала изучаются схема сети и реестр активов, а затем анализируется фактический трафик.

### 11.3. Мера МСЭ.2 — организация DMZ

Мера МСЭ.2 устанавливает требования к организации демилитаризованной зоны для компонентов, взаимодействующих с внешними сетями. В рассматриваемой схеме в DMZ размещается публичный веб-сервер. Сетевой обмен между внешними пользователями, DMZ и внутренними сегментами должен проходить через средства контроля. Разрешённые направления: пользователь → `WEB-GIS tcp/443`, затем `WEB-GIS → APP-GIS tcp/8443`.

При проверке этой меры выясняют, не открыт ли прямой путь EXT → APP/DB и не разрешён ли доступ из DMZ к хранилищу персональных данных. Особое значение имеет граница между веб-сервисом и внутренней сетью: именно она ограничивает дальнейшее распространение воздействия после возможной компрометации публичного компонента.

### 11.4. Мера МСЭ.3 — контроль сетевого доступа и фильтрация трафика

Мера МСЭ.3 связана с фильтрацией трафика на границах сегментов и внешних сетей. Её реализация для `FW-GIS` отражается в правилах по конкретным источникам, назначениям, протоколам и портам, а также в запрете остальных соединений. Контроль выполняется сравнением политики с согласованной матрицей, анализом журнала и проверочными подключениями.

Критерии П1–П6 переводят требования сегментации и фильтрации в проверяемые вопросы: существует ли запрет по умолчанию, не шире ли правило необходимого потока, проходит ли доступ через установленную границу, правильно ли организовано администрирование, ведётся ли регистрация событий и управляются ли изменения конфигурации.

## 12. Итоги лекции

Сегментация ГИС строится по функциональным зонам и контролируемым информационным потокам. Доступ к PostgreSQL предоставляется только назначенным прикладным и служебным узлам. Публичные соединения завершаются в DMZ, а административные подключения проходят через выделенный узел управления. Политика МЭ разрабатывается по матрице разрешённых потоков с запретом остального трафика, журналированием и регулярной проверкой.

Последовательность Э1–Э6 формирует полный порядок работы: инвентаризация, определение фактических потоков, проверка правил, оценка находок и повторный контроль после исправлений.
